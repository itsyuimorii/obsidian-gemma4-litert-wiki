<h1 align="center">Gemma Wiki</h1>

<p align="center"><em>Gemma 4 を LiteRT-LM + WebGPU で Obsidian の中だけで動かす、Karpathy パターンの LLM ウィキ。</em></p>

<p align="center"><a href="README.md">English</a> · <b>日本語</b></p>

<p align="center"><a href="https://gemma-wiki-demo.vercel.app"><b>▶ 動くところを見る</b></a> — 初回起動からウィキ完成まで全機能を 23 シーンで。インストール不要、矢印キーで進みます。</p>

**あなたのノートのための、無料・プライベート・オフラインな AI。** API キーもサブスクリプションも不要、トークン課金も一切なく、アカウント登録もありません。

Gemma 4 E4B は [LiteRT-LM](https://github.com/google-ai-edge/LiteRT-LM) と WebGPU を使い、Obsidian 自身のプロセスの中で動きます。Ollama でも LM Studio でも、localhost のサーバーでもありません — モデルはアプリの *中* にあります。**ノートがどこかにアップロードされることは決してありません。アップロード先のサーバーそのものが存在しないからです。** ここでのプライバシーは、ポリシーに書かれた約束ではなく、アーキテクチャの性質です。初回のダウンロード（約 3 GB のモデルと WebAssembly ランタイム。どちらも [プライバシー](#-プライバシー) に記載）を終えたあと、このプラグインが再びネットワークに触れることはありません。

このプラグインは **[Andrej Karpathy の LLM-wiki パターン](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)** を実装しています。あなたの生のノートが *モデルによって* 書き換えられることはありません — 不変性の制約が縛るのは LLM であって、あなたではありません。チャットで間違いに気づいたとき、自分でノートを直すのがごく普通の対処です（ウィキ側が変更を検知し、再取り込みを提案します）。その上に、相互リンクされた独立したウィキ層が作られます。ノート 1 枚につきカード 1 枚、そして **1 バイトでも書き込まれる前に、ページ全文が必ずあなたに提示されます。**

そこから先は、1 つのノート、あるいはウィキ全体を根拠にした対話、そのどちらからでも作れる小テスト、同じタグを共有するページ群をまたぐコンセプトページの生成、そして lint・来歴・矛盾チェックによる自己劣化の検出へと広がります。**出典はプラグインが列挙するものであり、モデルに引用させることは決してありません** — 引用は、小さなローカルモデルが誰にも気づかれないまま間違える、まさにその一点だからです。

書き出されるものはすべて、あなたの vault の中のプレーンな Markdown です。データベースに囲い込まれるものは何もなく、読み返すのに別のプラグインも要りません。設定自体もノートです。**タグ語彙と命名ルールは `schema.md` に置かれ**、手で編集すればプラグインはそれに従います。**すべての操作は `log.md` に追記され**、いつ何をしたのかを常に確認できます。そして **`skills/` に Markdown ファイルを置くだけで、⚡ メニューにあなた自身のコマンドが増えます。**

> **ステータス: 1.0.0。** [Andrej Karpathy の LLM Wiki パターン](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) の中核ループは実装され、動作しています。レビューを挟んで `gemma-wiki/` 層へ取り込み、相互リンクを張り、`gemma-wiki/index.md` のカタログと追記専用の `gemma-wiki/log.md` を保ち、インデックス優先で根拠を伴うチャットを行い、出典は決定的に付与されます。答えはそれを生んだ材料のそばに保存され（読み返すためのものであり、検索対象にはなりません）、モデルを使わない点検→修復パスと、単一タスクのスキルが揃っています。コミュニティプラグインストアに申請済みです。掲載されるまでは [リリース](../../releases) からインストールしてください。以下のベンチマークは実使用時の実測値です。

## ✨ 主な機能

**Karpathy ループ** — 生のノートは読み取り専用のまま、プラグインは独立した `gemma-wiki/` 層を保守します。

- **Ingest（取り込み）** — ノート 1 枚につき厳密な JSON 抽出を 1 回（要約、タグ、要点、目立つ言及、そして `high`/`med`/`low` の自己申告の確信度をフロントマターに記録）。加えて、インデックスのカタログから関連ページを選ぶ検証付きの多肢選択を行います。すべてレビューモーダルでプレビューされ、承認なしには何も書き込まれません。取り込み済みのノートにはファイルエクスプローラー上でバッジが付きますが、これは純粋な UI の装飾で、ノートのファイル自体には手を触れません。
- **Scan（半自動の取り込み）** — あなたが指定したフォルダを走査して新規・変更されたノートを見つけ、それぞれのカードを下書きし、**確信度の低い順に並べた** 1 つのリストでまとめてレビューします。人の目を最も必要とするページから読むことになります。ページにすべきでなかったものはチェックを外してください。範囲はオプトインです。フォルダ一覧を空のままにすると、vault 全体を走査するのではなく、Scan は実行を拒否します。
- **index.md / log.md** — クエリ経路が最初に読む、1 ページ 1 行のカタログと、追記専用で grep しやすい活動ログ。
- **Query（Wiki モード）** — ストップワードを除いたインデックス優先の検索。カタログと直近のログは常に同行するので、「今日は何を追加した？」のようなメタ質問も機能します。答えは検索された材料のみを根拠とし、それ以外は正直に断ります。
- **ウィキ全体への質問は、語彙が一致したページではなく全ページを根拠にします。** *「自分のページ同士は何でつながっているか」* はコレクションの形についての問いなので、ページ要約に対してスコアリングしても何も一致しません — 質問中の語がどの要約にも現れないからです。その結果モデルは 0 件のページを渡され、「何も与えられなかった」と正しく報告します。この種の問いを投げる 2 つのチップにはそのフラグが付いており、`loadPages` は予算いっぱいまで詰めて止まります。
- **答えをノートとして保存** — すべての返信に保存アクションがあります（同じレビューゲートを通ります）。保存先は **あなた自身のノート** で、元になったノートのそばに、`gemma — Summarize — The perfect espresso shot` のような名前で置かれます。ファイルエクスプローラーを見た瞬間に、モデルが書いたものであることと、何についてのものかの両方が分かります。さらにフロントマターには、どのモデルが、どの出典から書いたかが記録されます — コピー＆ペーストが静かに壊してしまう 2 つの情報です。保存先はあなたのフォルダ、あなたの整理体系の中であり、ウィキフォルダを削除しても生き残ります（プラグインが所有するものは、どれもそうは作られていません）。そして、あなたの普通のノートであるがゆえに、保存された答えがかつて決して持てなかった性質を持ちます — **取り込み可能である** ということです。Scan すれば他のノートと同じようにカードになります。これが、何かが材料になる唯一の経路です。ウィキが検索するものはすべて、あなたが書いたノートに由来するからです。
- **検索されうるものはすべて、あなたが書いたノートに由来します。** これは慣習ではなく構造として成り立っています。検索対象は `cards/`（取り込んだノート 1 枚につきカード 1 枚）と `concepts/`（それらのカードをまたいで作られる）だけです。
- **保存された答えが検索されることはありません。** Karpathy の gist は「探索は積み重なるべきだ」と述べていますが、信頼については何も述べていません。そこに汚染のループがあります — 誤った、あるいは古くなった答えが、ノートと同じ重みで文脈に再び入り込むのです。ですから保存された答えは検索対象にまったく含まれません。それはあなたの普通のノートであり、読み返すために保たれ、どのモデルがどの出典から書いたかをフロントマターに記録しています。戻ってくる経路はただ 1 つ、意図的で人間的なもの — あなたが内容を判断し、自分で書いた他のものと同じように取り込むことです。
- **コンセプトページ** — 2 つ以上のページが共有するタグや言及を選ぶと、プラグインはそれらの *上* に立つページを書き、各ページへリンクを張り下ろします。取り込みの影響はここまで波及し、メンバー一覧は双方向に自己修復します。

**正直さを保つ仕組み** — 誰もレビューしないウィキこそ、このプラグインが対抗しようとしている失敗の形です。

- **Review board（レビュー盤）** — ページが劣化する 3 つの経路を 1 つのキューにまとめます。自己申告の確信度が低いもの、**ソースのずれ**（取り込み後に生のノートが変更されたもの。`source_hash` で検出）、そして陳腐化。コンセプトの概要も対象です。
- **Provenance spot-check（来歴の抜き取り確認）** — ページの要点を生のノートまで遡り、それぞれの元になった文を探し、辿れなかったものにフラグを立てます。
- **Contradiction sweep（矛盾の走査）** — 同じタグを共有するページの組を調べ、食い違う主張を探します。最近変更された組から順に見ます。モデルの理由を引用してフラグを立てるだけで、**編集は一切しません** — どちらが誤りだったかを決めるのはあなたです。
- **Tidy the wiki（ウィキの手入れ）** — まず点検し、あなたがチェックしたものだけを直す 1 つのコマンドです。点検にモデルは使いません。孤立ページ、削除済みページを指しているインデックス項目、インデックスに載っていないページ、そしてページのタグが語彙からどれだけ離れたか。4 つの修復（リンクを相互にする、死んだインデックス項目を落とす、語彙を作り直す、それを既存ページに適用する）は常に提示され、点検が何かを見つけた項目には最初からチェックが入っています。各修復はそれぞれのプレビューを挟んで順番に実行されます。選択肢が検出結果に縛られることはありません。妥当な初期値を選ぶのに十分な点検であっても、唯一の入口として十分だとは限らないからです。
- **バックグラウンド計数**（既定でオフ） — 新規・変更されたノートの *件数* を定期的に数え、ステータスバーのチップに表示します。数えるだけでモデルは走りません。下書きが作られるのは、あなたがクリックしたときだけです。

**設定もノートとして** — ルールは、読めて、編集できて、バージョン管理できるプレーンな Markdown として存在します。

- **`schema.md`** — タグ語彙、命名ルール、そして **拒否リスト**。手で削除したタグは戻ってきません。*Organize tags* はローカルの Gemma に近い意味のタグを 1 つの語彙へ統合させ、*Retag* はそれを既存ページに適用します。どちらもプレビューを挟みます。
- **`skills/`** — ⚡ メニューの項目 1 つにつきファイル 1 つ。フロントマターに名前・アイコン・モードを書き、本文がプロンプトになります。本文中の `> [!info]` コールアウトはドキュメントであり、モデルに渡る前に取り除かれます。`fill: true` にすると、送信せずに入力欄にプロンプトを置いて待ちます — 何かに向けて狙いを定める必要があるスキル向けです。README と 2 つの例が同梱されており、これらには `stamp:` ハッシュが付いています。後のリリースで改善できますが、**あなたがそのファイルを編集していた場合はそのままです** — 以後それは永久にあなたのものになります。
- **すべてのフォルダに README があり**、そこに何を置くべきかを説明します。レイアウトは設定画面に行ごとの状態付きで表示され、scaffold が組み立てるのと同じ一覧から生成されます。

**チャットパネル** — shadcn 風のモノクロ、テーマ変数駆動。

- **2 つの根拠モード**: *This note*（開いているファイル）と *Wiki*（取り込み済みのページ群）。
- すべての答えに付く **決定的な Sources 行** — 実際に使われたものをプラグインが正確に列挙し、クリックできます。引用がモデルに委ねられることはありません。
- **`+` 添付** — 任意のノートをあいまい検索で選び、取り外せるコンテキストのピルとして追加できます。どちらのモードでも使えます。
- **⚡ Skills** — 単一タスクの定型プロンプト。*Quiz*、*Flashcards*、*Find gaps*、加えて編集可能なファイルとしての *Action items* と *Unclear bits*、さらに `skills/` に置いたものすべて。スキルファイルはフロントマターとプロンプトなので、メニューが持つのは *問い* です。何かを **する** もの（Scan する、ノートを取り込む、整形する）は、代わりに入力欄の上のチップになります。
- **スキルは必要なモードを自分で宣言し、モードが違うときは灰色になります。** 勝手にモードを切り替えたりはしません — メニュー項目が、パネルの根拠を黙って変えてしまうべきではないからです。同梱のスキルはすべてノート単位です。Wiki モードでは何も検索できなかったためで、語彙ベースのスコアラーはプロンプトの語をページ要約と突き合わせるのに、*「この教材から練習問題を作って」* は複利についてのページと語彙を 1 つも共有しないからです。
- **✨ Improve formatting** — 生のノートに書き込む唯一のアクションであり、このプラグインで最も制約の強い呼び出しです。構造・書式・誤字のみを対象とし、言い回しと文体は保存されます。書き込む前に結果全文をプレビューします。長いノートは見出しと空行で、それぞれコンテキストウィンドウに収まるパスへ分割され、1 パスずつ書き直されて縫い合わされます。選択範囲があれば 1 セクションに絞られます。
- **入力欄の上の 3 つの固定チップ** — パネルの中で決して消えない唯一の部分です。Wiki モードでは *Scan a folder*、*Find connections*、*What's still open?*。スキャン実行中は最初のものが **Stop scan** に変わります（コマンドパレットから始めた場合も同様）。ウィキが空でも並び替えは起きません。何も取り込んでいない状態でウィキに質問すれば「ここには何もありません」と答えますが、**その答え自体が、それを直すためのボタンを連れています。** 対処法が問題と一緒に移動するので、これが何なのかをまだ探っている人から他のチップを隠さずに済みます。
- 応答のストリーミング表示、入力中スピナー、停止ボタン、コピー／再生成、自動で伸びる・展開できる入力欄、チャットのクリア、各所のホバーツールチップ。

**プラグイン全体が従うエンジニアリング上のルール**:

- モデルへの操作はすべて **1 回の構造化された問い合わせ** です。ツールのループも多段の計画もありません。小さなローカルモデルは連鎖が苦手で、1 つのスキーマを埋めるのは得意だからです。
- **同時に走る操作は 1 つだけ。** エンジンもステータス行も時計も 1 つしかないので、2 つ目を始めようとすると、すでに何が動いているかを名指ししたメッセージとともに拒否されます。そして入口になりうる扉はすべて閉じます — チップは灰色になり、スキルメニューも何が動いているかを 1 行添えて灰色になり、チャット入力も受け付けません。ストリーミング中の応答も 1 つの操作として数えます。当初はそうなっておらず、応答の途中で *Formatting* を押すと同じ GPU 上で 2 つ目の呼び出しが始まっていました。
- すべての書き込みは **プレビュー→承認のゲート** を通ります。生のノートを変更する機能はちょうど 2 つ（Improve と Suggest tags & links）で、どちらも必ずプレビューされます。
- 根拠づけとは **材料が主題である** ということであり、モデルが使ってよい語彙がそれだけ、という意味ではありません。両モードとも同じ線を守ります。*あなたの材料* についての問いはそこからのみ答え、答えられないときは正直に断ります。*ある語の意味* についての問いは説明し、材料が述べていることと語の意味とを分けて示します。モードによって違うのは範囲であって、ルールではありません。Wiki モードでは、その区別が文面上で見えている必要があります。Sources 行が、あなたが今見ていないページを指しているからです。
- プロンプトは 4 つの場合を区別します。これらをひとまとめにすることが、小さなモデルが自信たっぷりに誤った拒否を返す原因だからです。材料が答えていない **事実の問い**（そう言う）、材料を使って作業せよという **指示**（実行する。フラッシュカードを求められて、ノートの *中* にフラッシュカードを探しに行き、断っていたことがありました）、ノートが使っている語の **説明の要求**（説明する。ノート自身の文をそのまま返すのは答えではありません）、そして **解釈できなかった要求**（理解できなかったと伝え、聞き直す）。最後のものが最も重要です。断片を投げると *「提供されたノートには X に関する情報がありません」* と返ってきていましたが、これはノートに情報があったかもしれないと示唆してしまいます。実際にはモデルが質問を理解できなかっただけなのに。
- 機能ごとの入力予算は、設定値からではなく **エンジンが実際に許可したコンテキストウィンドウ** から導きます。`Engine.create` から読み戻すのです。LiteRT-LM は `maxNumTokens` を切り詰めることがあり、要求値から導いた予算はその場合すべて上振れしてしまいます。
- **通知の語彙は 1 つ**（`src/notify.ts`）。6 種類がそれぞれ 1 つの意味だけを持ち、手で選んだ 10 個の数値ではなく 3 つの表示時間を使い、呼び出し側がミリ秒を決めることはありません。`noop` にはあえて印を付けていません — 正しく何もしなかったコマンドは、出来事ではないからです。失敗が生の例外を表示することはありません。操作の名前を挙げ、理由の 1 行目を示し、残りがどこにあるかを伝えます。警告とエラーは `log.md` にも追記されます。トーストは記録ではないからです。
- **3 つの面に、それぞれ 1 つの仕事。** トーストは *瞬間* なので、開始と結果を伝えます。実行は瞬間ではないので、進捗はステータスバーに置かれます。常に見えていて、ノートを覆わず、誤って消してしまうこともなく、クリックすればもう一度説明させられます。そして結果のダイアログが **自分から開くのは、あなたが一度も目を離さなかったときだけ** です。数分かかるスキャンの間にノートへ戻っていたなら、ダイアログはステータスバーで待ち、あなたが求めるまで、入力中の画面を奪ったりはしません。

## 💬 ノートと対話する — 完全にオフラインで

本と閃きのリボンアイコンをクリックするとサイドパネルが開きます。根拠モードは 2 つ、ピル型のトグルで切り替えます。

- **This note** — 現在開いているノートのみから答えます。
- **Wiki** — Karpathy の Query 経路です。まず `gemma-wiki/index.md` のカタログを読み、最も一致するページを読み込み、そこからのみ答えます（カタログと直近の活動ログも併せて渡されるので、「今日は何を追加した？」のようなメタ質問も機能します）。

どちらの場合も、答えは Obsidian 自身のプロセスの中で動くモデルからストリーミングで届きます。すべての答えの末尾には決定的な **Sources** 行が付き（クリック可能。モデルに引用させるのではなく、プラグインが列挙します）、メッセージごとに **コピー／再生成／ノートとして保存** のアクションがあります。両モードとも、材料があなたのノートについての問いに答えていないときは正直に断り、また材料が使っている語については、オウム返しにするのではなく説明します — 材料が述べていることと、語の意味とを分けたまま。**+** ボタンで追加のノートを、取り外せるコンテキストのピルとして添付できます。**⚡ skills** メニューは、開いているノートに対して単一タスクの定型プロンプト（*Quiz*、*Flashcards*、*Find gaps*）を実行します。

## 🤔 なぜ作ったのか

「ローカル AI」を謳う Obsidian プラグインの多くは、いまも独立して動く 2 つ目のアプリケーションに依存しています。プラグインが何かをする前に、Ollama や LM Studio をインストールし、バックグラウンドで起動しておかなければなりません。ノートが自分のマシンから出ていかないという意味ではローカルですが、「プラグインを入れればそれで動く」という意味ではローカルではありません。

このプロジェクトはもっと狭い問いを立てます。**Electron と WebGPU がすでに提供しているものだけを使って、モデルをプラグインとまったく同じプロセスの中で動かせるか？** 答えは、端から端まで検証した結果（[ベンチマーク](#-ベンチマーク) 参照）、短くて範囲の明確なテキスト処理については「はい」です。それが Karpathy 流のウィキ（実体・概念の抽出、相互参照、矛盾検出）を丸ごと支えるのに十分かどうかは、このプロジェクトが検証済みの一歩ずつ、公開されたコミット履歴の中で取り組んでいる、まだ開かれた問いです。

## 🔌 Ollama / LM Studio 系プラグインとの違い

|  | このプロジェクト | Ollama / LM Studio を使うプラグイン |
|---|---|---|
| **外部プロセス** | なし。モデルは Obsidian 自身のレンダラー内で動きます。 | Ollama / LM Studio を別途インストールして起動しておく必要があります。 |
| **セットアップ** | プラグインを入れるだけ。初回起動時にモデルを一度だけダウンロードします。 | プラグイン *と* 別アプリの両方を入れ、両者の接続を設定します。 |
| **API の面** | 設定するものはなく、推論 API もありません。ただし名前を挙げておくべき可動部が 1 つあります。WebGPU ランタイムには数ギガバイトの重みを HTTP 経由でしか渡せないため、プラグインはループバックサーバーを一時ポートで立て、自分のディスク上のモデルとランタイムのバイト列を自分自身に供給します。`127.0.0.1` にバインドし、推論エンドポイントは持たず、プラグインが読み込まれている間だけ存在します。 | `localhost:11434`（など）と HTTP で通信します。自分で起動し、設定し、動かし続ける別アプリです。 |
| **トレードオフ** | LiteRT-LM が今日サポートしているものにプラグインが縛られます。 | プロバイダーの選択肢は広がりますが、セットアップは重く、常駐アプリが 1 つ増えます。 |

これは「レンダラー内ローカルのほうが厳密に *優れている*」という主張ではありません。設計空間の中の別の一点であり、「完全にローカル」に意味があるのは出力の品質が保たれる場合だけです。以下のベンチマークが正直に確かめようとしているのは、まさにそこ — この手法が弱い箇所も含めてです。

## 📋 動作要件

- Obsidian 1.11.4 以降、**デスクトップ専用**（macOS / Windows / Linux。モバイル非対応。このプラグインは `isDesktopOnly: false` の形では公開されません）
- WebGPU が使える GPU とブラウザランタイム（Obsidian 同梱の Electron / Chromium）
- [`litert-community/gemma-4-E4B-it-litert-lm`](https://huggingface.co/litert-community/gemma-4-E4B-it-litert-lm) モデル用に約 3 GB の空きディスク容量。一度だけダウンロードされ、ディスクにキャッシュされます
- さらに LiteRT-LM の WebAssembly ランタイム用に約 20〜31 MB。初回使用時に取得されます。ランタイムは 4 種類のバリアントで配布されますが、あなたのマシンが読み込むのは常にそのうち 1 つだけで、どれを使うかはライブラリ自身の機能検査が決めます。ダウンロードされるのもその 1 つだけです
- ネットワークアクセスは、これらの初回ダウンロードのときだけ必要です。それ以降ネットワーク呼び出しは行いません

> **この vault を同期している場合は、モデルファイルを除外してください。** ダウンロード先は
> `<vault>/.obsidian/plugins/gemma-litert-wiki/gemma-4-E4B-it-web.litertlm` です。Obsidian は
> プラグインに vault の外の書き込み先を与えないためです。したがって iCloud、Dropbox、および
> 「コミュニティプラグイン」を有効にした Obsidian Sync は、いずれも約 3 GB をすべてのマシンへ
> 複製してしまいます。各マシンが自分で一度ダウンロードするほうが、はるかに短時間で済みます。
> ウィキフォルダ自体は普通の Markdown なので、通常どおり同期して問題ありません。
>
> なお `data.json`（ナレッジフォルダ名を保持しています）は同期されないことが多い点に注意して
> ください。片方のマシンでフォルダ名を変更しても、もう片方はそれを知りません。現在はウィキ
> らしきフォルダを見つけると、2 つ目を作る前に確認するようになっていますが、最もきれいな
> 対処は両方で同じ名前に変更することです。

## 🔧 仕組み

ローカルモデルを Obsidian のレンダラーの中で動かすと（既存の LiteRT-LM の Web 例がすべて動いている、Chrome 拡張の offscreen ドキュメントではなく）、通常のブラウザタブでは表面化しない Electron 固有の問題が 2 つ現れました。

1. **`file://` の script タグがブロックされる。** LiteRT-LM の WASM ローダーは、Emscripten のグルーコードを読み込むために `<script src="...">` タグを注入します。Obsidian 自身のページは `file://` オリジンから配信されておらず、Electron のローカルリソースガードは `file://` 以外のページから `file://` のスクリプトを読み込むことを拒否します。**対処:** `wasm/` ディレクトリを、プラグイン自身が起動する `127.0.0.1` のループバック HTTP サーバー経由で、寛容な CORS ヘッダー付きで配信します。

2. **WASM のグルーコードが自分のスクリプトのディレクトリを誤検出する。** `litertlm_wasm_internal.js` は Node.js 上で動いているかどうかを `typeof __filename` で判定します。Obsidian のデスクトップアプリは Node 統合された Electron レンダラーなので `__filename` は *定義されており*、しかもそれが指すのは Obsidian 自身の内部ファイルであって、動的に注入された WASM スクリプトではありません。これが正しい `document.currentScript` ベースのパス解決を乗っ取り、モデルバイナリの取得が、プラグインのサーバーではなく Obsidian 自身のページのオリジンを基準に解決されるほうへ静かにフォールバックしてしまいます。**対処:** `loadLiteRtLm()` を呼ぶ前に `self.Module.locateFile` をあらかじめ設定しておきます。ローダーは、自前の（この環境では壊れている）自動検出を走らせる前に、この上書きの有無を確認します。

読み込みが済んだあと、プラグインは Obsidian のセッションが続く間ずっと単一の `Engine` インスタンスを保持します（`src/main.ts` の `ensureEngine()` を参照）。これにより、約 3 GB のモデルと GPU のウォームアップのコストは、コマンドごとではなく一度だけ支払われます。

## 📊 ベンチマーク

数値はすべて `Conversation.getBenchmarkInfo()` によるもの — 推定ではなく LiteRT-LM の実計測であり、ベンダー公称値ではなく実機での測定です。

| シナリオ | Prefill | Decode | 最初のトークンまで |
|---|---|---|---|
| コールドエンジン、入力 2098 トークン | 74.7 tok/s | 29.1 tok/s | **28.1 秒** |
| ウォームエンジン、入力 1558 トークン | 495.0 tok/s | 28.9 tok/s | 3.2 秒 |
| ウォームエンジン、入力 274 トークン | 386.5 tok/s | 29.5 tok/s | **0.74 秒** |
| ウォームエンジン、入力 634 トークン（段落全体） | 494.7 tok/s | 29.1 tok/s | 1.3 秒 |

**読み取れること:** ごく最初の呼び出しに現れる約 28 秒というコールドスタートの数字は、GPU のシェーダーコンパイルと重み変換にかかる一度きりのコストであり、呼び出しごとの税ではありません。エンジンが温まれば prefill のスループットはおよそ 5〜6 倍に跳ね上がり、短い選択範囲のレイテンシは 1 秒を切ります。decode 速度（約 29 tok/s）は入力長にもウォーム／コールドにも関係なく安定しています。

**品質** は、6 つの英語テスト文（基本的な誤字、微妙な文法、誤りがゼロの文、箇条書き、*直してはいけない* 専門用語、そして最終段落に誤りが散らばった 700 語の記事）に対して手作業で確認しました。見落とした誤りゼロ、幻覚による変更ゼロ、すでに正しい文では完全一致の出力、専門用語とリストの書式はすべて保存され、長文の最初の段落と最後の段落とで品質の低下はありませんでした。

**構造化出力の信頼性**: 貪欲サンプリングで独立に 5 回実行し、5/5 が妥当で形の正しい JSON（`{"summary": string, "tags": string[3]}`）を返しました。取り込みパイプラインを成り立たせる、荷重を支える前提です。

## 🗺️ ロードマップ

実装済み — Karpathy の中核ループを、小さなオンデバイスモデルが担えると検証できた範囲に意図的に絞っています。

- **Ingest**: レビューゲート付き（承認なしには何も書かない）、単一スキーマの抽出、インデックスのカタログから選ぶ関連ページの相互リンク、ページのフロントマターに記録される確信度。
- **Query**: ストップワードを除いたインデックス優先の検索、カタログと活動ログが常に文脈に入ること、決定的な出典表示、そして答えを自分のノートへ保存すること — 読み返すためのものであり、意図的に根拠としては戻しません。
- **Tidy**: できる限りモデルを使いません。孤立ページとインデックスの健全性はモデルなしで点検され、4 つの修復はあなたがチェックしたものだけを実行します。

かつて「次にやること」として挙げていたものは、すべて実装済みです。ユーザー定義スキル（`skills/` にファイルを置く）、モデル支援による矛盾候補の抽出（人間の判断に委ね、自動修正はしません）、スキャンにおける内容ハッシュによる重複除去ゲート、そしてレビュー盤。実際に残っているのはコミュニティストアへの申請そのもので、現在審査中です。

意図的に対象外としているもの: 複数プロバイダーの抽象化層、画像入力（LiteRT-LM の Web ランタイムがまだ対応していません）、PDF の OCR、そして「インデックスを読み、それが指すページを読む」より複雑な検索方式。フラットインデックスの限界は現場報告でおよそ 77 ページ前後とされており、このウィキの現在の規模をはるかに上回ります。その判断はそこに達したときに見直すのであって、それ以前ではありません。

## 🔒 プライバシー

バックエンドなし、テレメトリなし、アナリティクスなし。このプラグインがネットワークリクエストを行う先はちょうど 2 つのホストだけで、どちらも動作に必要なものの一度きりのダウンロードであり、どちらもそのあとディスクにキャッシュされます。

| ホスト | 何を | いつ |
| --- | --- | --- |
| `huggingface.co` | [Gemma 4 E4B モデル](https://huggingface.co/litert-community/gemma-4-E4B-it-litert-lm)（約 3 GB） | **Download model** を押したとき、一度だけ |
| `cdn.jsdelivr.net` | LiteRT-LM の WebAssembly ランタイム（約 20〜31 MB）。このビルドがコンパイル対象としたピン留め済みの `@litert-lm/core` バージョンから | 初回使用時、一度だけ |

ランタイムを同梱せず取得しているのは、合計約 101 MB の 4 バイアントで配布されているのに、あなたのマシンが読み込むのはライブラリ自身の機能検査が選ぶちょうど 1 つだけだからです。4 つすべてを同梱すれば、その 5 分の 1 を使うために 101 MB のペイロードをすべてのインストールに載せることになります。受け入れられるのは `litertlm_wasm_*internal.{js,wasm}` に一致するファイルだけで、ここでプラグイン自体が更新されることはありません。バージョンはビルド時に固定されます。

プラグインは **ループバック HTTP サーバー** も実行します（`127.0.0.1`、一時ポート、プラグインが読み込まれている間だけ生存）。これが存在するのは、WebGPU ランタイムにモデルを渡す手段が HTTP しかないためです。あなた自身のディスク上のファイルを、あなた自身のマシンに配信するだけで、推論エンドポイントはなく、外部から到達することもできません。

**それ以外に、あなたのマシンから出ていくものはありません。** ノートも、質問も、生成されたすべての答えも端末上に留まります。推論もキャッシュも生成も、すべて Obsidian 自身のプロセスの中で起きます。アップロードする先のサーバーが存在しません。
